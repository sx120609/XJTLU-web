# 迭代一：付费学习资料交易闭环

## 1. 产品目标与范围

本迭代把学习资料从历史免费领取兼容链路升级为“审核创作者发布、买家直付创作者、平台留存凭证并负责交付和售后状态”的付费数字内容闭环。

本迭代完成：

- 创作者准入、收款方式和资料版本审核；
- 资料定价、付费下单、付款凭证、人工确认和受控下载；
- 买家、卖家和管理员三端订单工作台；
- 售后问题、人工退款登记、访问权撤销和全链路审计；
- 幂等、并发锁、私密文件权限和灰度开关。

本迭代不做：

- 平台代收、钱包、余额、提现、自动分账或默认抽佣；
- 自动识别到账、自动退款或支付网关回调；
- 绕过版权审核的即时发布；
- 删除历史免费领取数据。

## 2. 角色与职责

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 买家 | 浏览已上架资料、下单、查看收款码、上传付款凭证、下载已购版本、确认完成、发起售后 | 查看其他订单的收款码/凭证、未交付先下载、改写价格 |
| 创作者 | 申请资格、配置支付宝/微信收款码、发布和提交资料版本、确认/驳回凭证、处理售后 | 未审核发布、确认他人订单、修改已下单快照 |
| 审核员/管理员 | 审核创作者与资料、在争议订单中核验凭证、处理售后和登记退款 | 触发真实扣款、替代创作者收款、无审计改写终态 |
| 平台 | 固化快照、控制访问、记录事件、通知参与方、限制非法状态转换 | 代收资金、自动判定线下资金已到账 |

## 3. 主工作流

### 3.1 创作者准入

1. 用户提交擅长领域、经验、样例说明和版权承诺。
2. 系统只允许一条有效申请进入审核，重复并发提交由事务锁串行处理。
3. 审核员批准后创建或恢复 `active` 创作者档案；驳回必须填写原因。
4. 只有 `active` 创作者可以新增收款方式、创建付费资料或提交版本审核。
5. 收款码使用私密资产存储；停用收款方式后不得用于新订单，历史订单快照不变。

### 3.2 资料发布与版本审核

1. 创作者填写标题、介绍、课程信息、原创性声明、售价和文件。
2. 售价以整数分保存，必须处于环境配置的最小/最大价格之间，不能以 `0` 元绕过付费链路。
3. 每个新版本单独提交审核；审核清单必须同时通过版权、内容质量和文件安全。
4. 审核通过后才允许资料公开上架；驳回保留原因，创作者修订后提交新版本。
5. 已购订单绑定下单时版本，后续发布新版本不得悄悄替换历史交付物。

### 3.3 下单、付款与交付

1. 买家选择支付宝或微信，系统校验资料、版本、创作者和对应收款方式均有效。
2. 服务端使用 `Idempotency-Key` 创建唯一订单，固化价格、版本、卖家、收款方式和到期时间。
3. 买家只能通过鉴权接口查看该订单的收款码，线下直接向创作者付款。
4. 买家上传付款截图和可选说明；凭证为私密资产，同一幂等键不会重复创建。
5. 创作者核验后确认：
   - 凭证变为 `accepted`；
   - 订单变为 `delivered`；
   - 系统授予订单版本的下载访问权；
   - 写入订单事件并通知双方。
6. 创作者驳回时必须说明原因，订单回到 `pending_payment`，买家可以重新提交凭证。
7. 争议场景下，审核员/管理员可以查看凭证并代为确认或驳回。
8. 买家确认完成后订单进入 `completed`；存在未关闭售后时禁止完成。

### 3.4 售后与退款

1. 订单参与方可发起交付、内容、版权、付款、退款或其他问题。
2. 活动售后将订单置为或保持 `disputed`，并阻止买家确认完成。
3. 管理员可以：
   - `resolve`：记录解决方案并恢复可继续履约状态；
   - `close`：关闭无效或撤回问题；
   - `record_refund`：核验线下退款后登记金额。
4. 登记退款时必须校验金额为正且不超过订单实付金额；订单进入终态 `refunded`。
5. 退款事务同时撤销该订单授予的资料访问权、关闭活动售后、写入退款时间和事件，并通知双方。
6. 系统不自动转账。真实退款由创作者线下完成，后台动作仅用于核验、留痕和收回数字权益。

## 4. 状态机

订单允许的状态转换：

| 当前状态 | 可进入 |
|---|---|
| `pending_payment` | `awaiting_seller_confirmation`、`cancelled`、`expired` |
| `awaiting_seller_confirmation` | `pending_payment`、`disputed`、`delivered`、`refunded`、`cancelled` |
| `disputed` | `pending_payment`、`delivered`、`refunded`、`cancelled` |
| `delivered` | `completed`、`refunded` |
| `completed` | `refunded` |
| `refunded` | 无，终态 |
| `cancelled` | 无，终态 |
| `expired` | 无，终态 |

付款凭证状态为 `submitted -> accepted | rejected | superseded`。售后状态为 `open | waiting_buyer | waiting_seller | refund_requested -> resolved | closed | refund_recorded`，其中 `refund_recorded` 是已登记退款的终态。

任何状态转换都必须在服务端根据当前数据库状态判断，前端按钮只负责表达意图，不能作为权限或状态依据。

## 5. 全栈实现边界

- 数据层：新增创作者、私密资产、收款方式、审核、付款凭证、订单事件、售后和幂等命令模型；旧资料表使用 `legacy_free | paid` 区分兼容模式。
- 服务层：统一价格单位、序列化、状态转换、事务锁、幂等命令、访问授权和通知。
- API：付费交易挂载在 `/api/market/materials/commerce`，原资料公开 URL 保持兼容。
- Web：资料详情、发布页、创作者中心、买卖订单中心和管理后台使用同一套订单状态及动作契约。
- 文件安全：收款码、付款凭证等资产不进入公开上传目录；响应使用鉴权、`private, no-store` 和 `nosniff`。
- 商业边界：`commissionBps` 与 `learningMaterialCommissionBps` 固定为 `0`，平台不从资料交易抽成。

## 6. 发布与回滚工作流

### 发布前

1. 备份生产数据库，并确认可恢复。
2. 在空 PostgreSQL 库执行全部迁移和种子，确认迁移状态为最新。
3. 执行服务端单元测试、18 组真实 PostgreSQL 集成测试、两端类型检查和生产构建。
4. 配置私密资产目录的持久化、权限、备份与容量监控。
5. 保持 `PAID_LEARNING_MATERIALS_ENABLED=false` 部署代码和迁移，先验证后台及历史数据兼容。

### 灰度开启

1. 设置价格区间、付款/确认/完成时限。
2. 先审核少量创作者和资料，培训审核员按三项清单操作。
3. 设置 `PAID_LEARNING_MATERIALS_ENABLED=true`，仅放量给首批资料。
4. 监控下单成功率、凭证驳回率、平均确认耗时、售后率、退款率、重复命令和私密资产访问拒绝。

### 紧急关闭

1. 将 `PAID_LEARNING_MATERIALS_ENABLED=false`，立即阻止付费版本提交、新下单、提交付款凭证和确认交付；创作者准入资料仍可在后台准备。
2. 不回滚已应用数据库迁移，不删除订单、凭证、售后或访问记录。
3. 存量订单继续可查询，已交付订单和售后仍按状态机处理；待付款或待确认订单由运营通知双方暂停处理，修复重开后继续，必要时按售后流程取消或退款。
4. 修复并验证后重新灰度，不通过手工 SQL 跳跃订单状态。

## 7. 验收清单

- [x] 未审核用户不能发布付费资料或配置有效收款链路。
- [x] 资料未经三项审核不能公开售卖。
- [x] 售价非零、以分存储、上下限由配置控制。
- [x] 收款码和付款凭证不能通过公开静态路径访问。
- [x] 重复下单、重复提交和重复确认保持幂等。
- [x] 并发审核与确认不会生成重复记录或覆盖终态。
- [x] 卖家确认后才授予对应版本下载权。
- [x] 活动售后阻止订单完成。
- [x] 退款金额经过校验，退款后订单终结且下载权撤销。
- [x] 买家、卖家、审核员和管理员的数据可见性彼此隔离。
- [x] 历史免费资料数据可兼容读取，但不能产生新的免费领取。
- [x] 空库迁移、种子、真实 HTTP 冒烟和全量 PostgreSQL 集成通过。

## 8. 下一迭代入口

迭代二优先基于真实运营数据完善：

1. 创作者分级、资料质量评分和违规累计处置；
2. 订单超时调度、审核 SLA 看板和异常提醒；
3. 退款凭证附件、证据补充轮次和更细售后责任归因；
4. 资料水印、下载次数与设备异常检测；
5. 前后端契约自动生成和浏览器端关键流程自动化；
6. 在合规评估通过前，继续保持平台代收、钱包和自动分账不在范围内。
