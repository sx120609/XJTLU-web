# 靠浦全项目重构蓝图（2026-07-28）

## 1. 本轮目标

本轮不再围绕单个页面或接口修补，而是把当前仓库当作一个长期叠加形成的系统重新建模。重构必须保留已有业务数据、公开链接和核心安全边界，并通过小步、可回滚的提交逐步替换内部结构。

以下事实以当前代码为准，不以旧阶段报告为准：

- 主应用是 `web/` 的 Vue 3 前端和 `server/` 的 Express + Prisma 服务端。
- 服务端现有 138 个 TypeScript 源文件、30 个路由文件、87 个服务文件和 93 个 Prisma Model。
- Web 端现有 110 个 Vue 文件，其中 79 个页面视图；多个核心页面超过 1,000 行。
- 最大服务端文件已达到 2,000—3,600 行，`admin`、`market`、`tools`、`qqbot` 和 `filestore` 是主要复杂度热点。
- `createApp()` 曾直接启动多类定时任务和外部连接，HTTP 组装、进程生命周期和后台任务没有分层。
- 旧 JWXT 路由已不再挂载，但旧课表、教务页面和配套 API 仍保留在前端；删除前需要用真实访问数据确认。
- Android/Harmony 仍混有旧 CPU/“药大课表”标识；Flutter 是较新的靠浦客户端线。
- `desktop/` 是学习通刷课助手，产品、依赖和发布方式均与 XJTLU 校园平台不同，应作为独立遗留产品处理。
- 当前没有 CI 工作流、前端组件测试和统一的前后端契约生成；13 个服务端测试文件主要通过读取源码做静态断言。
- 集成测试依赖外部 PostgreSQL；数据库不可用时没有统一预检，会重复等待并产生大量次生 500。

## 2. 不可破坏的边界

1. XJTLU 密码只用于当次认证请求，不写入数据库、日志或服务端缓存。
2. 学生实体商品款不经过平台，不引入钱包、提现或默认抽佣。
3. 学习资料主线已由迭代一升级为审核制付费原创资料；买家直付创作者，平台不代收、不抽佣，权利声明和文件安全审核继续作为强约束。详见 `iteration-1-paid-learning-commerce-workflow.md`。
4. 不在重构提交中执行破坏性数据库迁移；所有 Schema 变更必须先有备份、兼容读写和回滚方案。
5. 旧公开 URL、原生壳 Bridge 和现有 API 在宣布迁移窗口前保持兼容。
6. 当前工作区中未提交的 XJTLU 学术服务改动和论坛上传文件不由重构过程覆盖或清理。

## 3. 目标架构

主服务继续采用模块化单体，暂不拆微服务。目标域如下：

| 领域 | 主要职责 |
|---|---|
| `identity` | 站内会话、XJTLU SSO、用户、权限与隐私授权 |
| `community` | 广场、板块、帖子、回复、消息、审核与公告 |
| `marketplace` | 商品、求购、匹配、履约、信任、商户与推广 |
| `learning` | 付费原创资料、创作者准入、版本审核、订单、受控文件访问与售后 |
| `campus` | eHall、eBridge、校园资源和学校侧适配器 |
| `tooling` | 问卷、成绩核对、文件收集、PDF 与 QQ 提醒 |
| `operations` | 管理后台、站点配置、健康、审计和数据维护 |
| `platform` | 数据库、缓存、媒体存储、任务运行器、HTTP 和可观测性 |

每个服务端领域逐步收敛为 `router -> application service -> repository/adapter`，路由不直接承载大段事务和序列化逻辑。Web 端按同样领域建立 `features/`，页面只负责组合视图，API 契约、状态和可复用组件跟随领域放置。

前后端共享的请求/响应类型应进入独立 `contracts` 包，并由 Zod Schema 生成 TypeScript 类型；在完成迁移前，旧 API 类型继续兼容。

## 4. 分阶段路线

### 阶段 A：护栏和运行基线

- 将 Express 工厂、启动准备和后台 Worker 分离，保证测试导入应用时不产生定时器和外部连接。
- 统一 CORS、Cookie、CSRF 和可信代理配置的真实行为与文档。
- 给集成测试增加数据库预检和隔离数据库自举；本地缺少依赖时快速给出单一、可操作的错误。
- 建立 CI：类型检查、单测、临时 PostgreSQL 集成、前端构建、Bundle 预算和依赖审计。
- 固定项目体量、测试数量、迁移数量和公开路由清单作为后续对比基线。

验收：`createApp()` 无后台副作用；单元测试不依赖数据库；集成环境可一条命令自举；所有失败均能定位到具体阶段。

### 阶段 B：服务端模块化

- 先拆 `market.ts`、`admin/index.ts` 和 `tools.ts`，每次只迁移一个子域并保持原 URL。
- 把路由内事务、参数解析和响应映射移到应用服务。
- 解除 `storageConfig -> oneDriveChina -> mediaStorage` 的循环依赖，引入明确的存储端口和适配器。
- 建立统一错误码、分页、幂等和审计上下文。

验收：核心路由文件原则上小于 300 行；领域之间只能通过公开接口依赖；不存在源码级循环依赖。

### 阶段 C：数据模型治理

- 先在应用层集中定义状态、角色、类型和可见性 Schema，再逐步增加数据库约束。
- 将高频查询使用的 JSON 字符串字段迁移为结构化列或 PostgreSQL `Json`，保留兼容读路径。
- 分析 93 个 Model 的实际使用和索引命中，不以“表已存在”为保留理由。
- 把启动时的数据补齐移到显式、幂等的数据迁移命令。

验收：非法状态无法进入写路径；迁移可在生产快照副本演练；应用启动不再隐式改写业务数据。

### 阶段 D：Web 信息架构与组件治理

- 建立单一导航/路由元数据源，消除桌面、移动端和原生壳入口的重复定义。
- 优先拆分 `SchedulePane`、`ToolManage`、`Topic`、`MainLayout` 和管理后台大页面。
- 为登录、发布、交易、课表和管理操作增加组件/浏览器测试。
- 使用共享契约替代前后端手写重复接口。

验收：核心页面有加载、空态、失败和权限测试；页面组件不再同时承担请求、缓存、业务规则和大段渲染。

### 阶段 E：学校适配器与后台任务

- eHall、eBridge、公告、Weiwall、QQBot 和媒体审核统一实现为适配器与 Job。
- Job 注册中心统一负责单例启动、分布式锁、超时、重试、停止和健康状态。
- 上游 HTML/协议解析使用脱敏 Fixture 做契约测试，避免线上结构变化直接破坏页面。

验收：进程可优雅停止；每个 Job 可独立运行和观测；上游失败不会拖垮 HTTP 主服务。

### 阶段 F：多端和仓库边界

- 以 Flutter 作为候选正式移动壳；旧 Android/Harmony 进入仅兼容或归档状态，由真实安装量决定。
- 统一品牌、域名、包名、Bridge 命名和版本来源。
- 将 `desktop/` 移出主应用发布链，最终迁入独立仓库或明确归档。
- 禁止继续提交 Electron 解包目录、运行时报告和用户上传物。

验收：每个发布产物只有一个责任人、版本源和构建命令；主应用发布不再携带无关桌面产品。

## 9. 市集求购响应与预约切片

第四个领域切片覆盖卖家响应、求购者决策和预约创建，并修复原实现中的并发窗口：

- 将 `POST /wanted/:id/responses` 和 `PATCH /wanted-responses/:id` 迁入 `routes/marketWantedResponse.ts`，原 URL、认证方式、请求体、响应信封和返回对象保持不变；
- 新增 `services/marketWantedResponseService.ts`，统一编排响应创建/撤回/拒绝/接受、定向商品、求购状态、其他待处理响应、购买意向、预约订单、交易会话和通知；
- 新增求购事务锁服务，对同一求购的响应创建和状态转换使用 PostgreSQL 事务级 advisory lock；重复并发响应只能成功一次，同时接受不同响应也只能生成一笔预约；
- 接受响应时对求购、商品和目标响应继续使用条件更新，即使生命周期清理或其他商品交易并发发生，也会整笔回滚而不会留下“多笔预约”“商品已锁但求购未匹配”等半完成状态；
- 求购编辑和续期/结束也接入同一锁，并在提交前复核 `updatedAt` 与合法状态，避免用户结束求购和接受响应互相覆盖；
- 将订单号生成、订单敏感字段序列化、旧收款资料加解密和市集通知提取为共享服务；通知仍在事务提交后尽力发送，不因通知故障回滚已完成交易；
- Web API 新增 `WantedResponseInput`、`WantedResponseAction` 和 `WantedResponseActionResult`，详情页与“我的市集”复用同一动作类型，成色字段收窄到既有 `MarketCondition`；
- 增加 Schema、敏感字段可见性、非法路由 ID、事务锁键和源码契约测试，并在真实 PostgreSQL 集成用例中增加“同一卖家并发重复响应”及“两个响应被同时接受”的竞争测试；
- 主 `market.ts` 从 1,982 行降至 1,709 行；106 条服务端端点和 84 个 Web 调用仍全部匹配，无同方法重复路由。

本切片本地通过服务端 109 个单元/契约测试、两端类型检查、服务端/Web/桌面生产构建、Web Bundle 预算和差异格式检查。真实并发集成用例需要隔离 PostgreSQL；本机 `127.0.0.1:55433` 未启动时预检会快速退出，CI 使用临时 PostgreSQL 16 从零迁移后执行。下一切片应处理普通商品的购买意向、报价和预约创建，使三条交易入口共享同一商品锁与订单应用服务。

## 10. 市集商品意向与报价切片

第五个领域切片覆盖当前购买意向和旧客户端报价兼容入口，并将三条实体商品成交路径收敛到同一商品状态边界：

- 将 `POST /items/:id/intents`、`PATCH /trade-intents/:id`、`POST /items/:id/offers` 和 `PATCH /offers/:id` 迁入 `routes/marketTrade.ts`；
- 新增 `services/marketTradeService.ts`，集中处理身份/发言限制、商品可交易性、议价规则、重复提交、状态转换、零平台费预约、交易会话和事务后通知；
- 新增商品事务锁服务；购买意向、旧报价、求购响应，以及商品编辑、下架、标记已售和兼容删除都使用同一 PostgreSQL 事务级 advisory lock；
- 同一买家并发提交重复购买意向时只创建一条待处理记录；不同入口同时接受同一商品时只有一个事务能锁定商品并创建订单；

- Web API 新增 `MarketOffer`、`MarketTradeIntentInput`、`MarketOfferInput` 和 `MarketTradeAction`，商品详情与“我的市集”不再各自手写动作联合类型；
- 增加 Schema、序列化、商品锁键、非法路由 ID、跨模型关闭规则和前端契约测试；真实 PostgreSQL 集成用例增加重复意向并发，以及当前意向与旧报价同时接受的竞争测试；
- 主 `market.ts` 的非空代码行从 1,709 行降至 1,583 行（物理行 1,673 行）；106 条服务端端点和 84 个 Web 调用仍全部匹配，无同方法重复路由。

本切片本地通过服务端 110 个单元/契约测试、两端类型检查、服务端/Web/桌面生产构建、Web Bundle 预算和差异格式检查；Web 初始资源 gzip 体积为 379.7 KiB，低于 700 KiB 预算。新增的真实并发集成用例需要隔离 PostgreSQL；本机 `127.0.0.1:55433` 未启动时预检会快速退出，CI 使用临时 PostgreSQL 16 从零迁移后执行。下一切片应迁移预约订单的时间地点、双方确认、取消、爽约和退款兼容状态，使订单履约与生命周期清理共享订单级锁。

## 11. 市集订单履约切片
