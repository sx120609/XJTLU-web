# 「靠浦」校园平台产品定位重构——阶段 0 全量审计报告

> 历史说明：本文记录阶段 0 当时的审计结论，其中“免费学习资料”方案已被迭代一的付费原创资料方案取代。当前产品与开发验收以 `iteration-1-paid-learning-commerce-workflow.md` 为准。
>
> 审计日期：2026-07-18
> 当前阶段：阶段 0（只审计、规划，不修改业务逻辑和数据库）
> 目标定位：以校内二手与求购交易为核心，校园广场、学习资源、校园服务为补充的综合校园平台

## 0. 审计范围与结论

本次已检查仓库中的前端、服务端、Prisma 数据模型与迁移、路由、权限、中间件、核心业务接口、测试、PWA、Android / Flutter / HarmonyOS 壳、桌面端项目和部署脚本。依赖目录、编译产物、二进制资源没有逐文件审阅；它们不属于本次产品与业务源码审计范围。

当前仓库不是一个需要推倒重写的空壳。论坛、市场、私信、通知、举报、内容审核、校园认证、文件存储、公告同步和后台管理均已有可复用基础。真正的问题是：

1. 产品主入口仍以论坛、公告、校园工具为中心，二手交易只占次要位置。
2. 市场的实体商品交易被设计为“平台收款—退款—结算—提现”，与新定位中“只撮合、不碰学生商品款”直接冲突。
3. 求购、学习资料、校园服务虽已有部分能力，但数据结构与目标业务不匹配。
4. 存在发布前必须先处理的隐私、认证、死链和数据库迁移风险。

因此推荐策略是：**保留 Vue / Express / Prisma 架构和现有品牌 UI，先冻结错误商业链路，再按入口、状态机、内容结构逐层改造。**

### 基线验证

| 检查 | 结果 | 说明 |
| --- | --- | --- |
| `npm run verify:full` | 通过 | 39 项单元测试、2 项集成测试、服务端类型检查、前端生产构建均通过 |
| `npx prisma validate` | 通过 | 当前 Prisma schema 语法有效 |
| 市场数据库完整性检查 | 部分通过 | 当前无市场订单/支付数据，易支付未启用；学习资料检查发现实体商品基础佣金配置为 5%，不符合“实体商品佣金必须为 0” |

| Git 工作区基线 | 干净 | 审计前没有未提交改动 |

### 当前本地数据库数据概况

当前数据库不是纯空库：3 个用户、14 个板块、200 条校园公告、2 个论坛图片资源、10 个学习资料类型、9 个市场分类；帖子、回复、市场商品、订单、支付日志目前均为 0。审计仅进行了只读统计，没有读取或在报告中披露账号、密钥和会话原文。

## 3. 当前路由结构

### 3.1 前端路由

当前约有 47 个显式路由记录，主要分组如下：

| 分组 | 现有路由 | 问题 |
| --- | --- | --- |
| 认证 | `/login`、`/register` | 基础可用；需调整凭证记忆策略 |
| 首页 | `/home` | 大 Hero、论坛/公告/工具优先，交易预览权重低 |
| 论坛 | `/forum`、`/forum/hot`、`/forum/latest`、`/forum/b/:slug`、`/forum/topic/:id`、`/post` | 12 个社区板块，结构过重；需收敛为 4 类校园广场 |
| 市场 | `/market`、`/market/item/:id`、`/market/publish`、编辑、我的、卖家中心、消息 | 实体交易基础较完整，但绑定平台支付/结算 |
| 学习资料 | `/market/learning-materials`、发布、购买、资料库、售后 | 当前为付费数字商品，必须转为免费原创资源中心 |
| 校园资源 | `/services`、`/academic`、`/announcements`、工具与问卷/文件收集 | 能力较多，但不应继续占主导航一级入口 |
| 用户 | `/messages`、`/profile`、`/u/:id`、QQ 提醒 | 可作为“我的”聚合页基础 |
| 管理 | `/admin` | 功能丰富，但缺少统一审核队列、交易状态治理和管理员操作审计 |
| 其他 | `/search`、`/sponsor-wall` | 搜索覆盖不足；赞助墙不应与学生商品交易支付混用 |

### 3.2 明确死链与残留路由

- 前端和原生壳多处引用 `/schedule`、`/jwxt`，但主 Vue Router 没有注册这两个页面。
- 服务端保留了完整 `jwxtRouter`，但主路由没有挂载 `/api/jwxt`；现有测试还明确断言旧接口返回 404。
- `ServiceCard` 的 `ACAD_PORTAL` 会被标准化为 `/jwxt`，因此校园服务卡也可能跳到 404。
- Android 和 HarmonyOS 默认打开 `/schedule`；Flutter 底栏仍固定包含 `/jwxt`、`/schedule`。
- 桌面端调用 `/auth/sso-begin`、`/auth/sso-login`，当前服务端已不再挂载这些旧接口。

这些代码不是立即删除对象。阶段 0.5 应先决定：恢复为兼容跳转，或彻底取消入口并清理提示文案，不能继续处于“代码存在但产品不可达”的状态。

### 3.3 后端路由

当前主 API 已挂载：认证、用户、板块、帖子、回复、点赞、消息、服务、课程、搜索、首页、站点设置、存储、工具、支付、QQ Bot、微墙授权、Course Bot、eHall / academic、市场和后台。

市场 API 同时包含：商品、收藏、议价、订单支付、回调、退款、结算、提现资料、会话、消息、评价、举报、学习资料和后台配置。目标改造应先在现有 `/api/market` 内保留兼容响应，再逐步抽出 `/api/listings`、`/api/wanted`、`/api/trade-intents` 等清晰域接口，避免一次性破坏旧前端。

## 4. 当前数据库实体与目标映射

### 4.1 当前实体分组

| 领域 | 主要模型 | 现状 |
| --- | --- | --- |
| 用户 | `User`、`MessageSetting`、`Notification` | 用户、角色、校内 SSO 验证状态已存在，但没有独立认证档案和资料档案 |
| 论坛 | `Board`、`Topic`、`Reply`、`Like`、`Tag`、图片/视频、AI 审核日志 | 能力完整，可作为校园广场底层 |
| 市场 | `MarketItem`、图片、收藏、报价、订单、会话、消息、评价、举报 | 基础可复用，但商品、求购和平台支付状态耦合 |
| 市场支付 | `MarketPaymentLog`、`MarketRefund`、`MarketSettlement`、`MarketPayoutProfile`、`MarketConfig` | 与新边界冲突，必须冻结但保留历史数据 |
| 学习资料 | 类型、档案、版本、文件、访问权、工单与消息 | 版本与文件可复用；购买访问权与佣金逻辑要退出 |
| 校园资源 | `ServiceCard`、公告、课程、工具、问卷、成绩核对、文件收集 | 能力分散，需要重新聚合为首页资源区和“我的工具” |
| 支付 | `EpayConfig`、`SponsorOrder`、`SponsorPaymentLog` | 可仅保留给平台自己的推广/赞助费用，禁止用于学生商品款 |
| 运维 | 站点设置、QQ Bot、Course Bot 配额、管理员每日登录 | 缺统一管理员操作审计和全站业务事件统计 |

### 4.2 目标数据模型建议

为降低风险，第一轮不做大规模物理表重命名，先做“语义迁移 + 增量字段/表”：

| 目标模型 | 复用/新增方案 | 关键字段或关系 |
| --- | --- | --- |
| `User` | 保留 | 账号、角色、状态；公开序列化禁止暴露学校登录名 |
| `UserProfile` | 新增或从 `User` 渐进拆分 | 昵称、头像、校区、学院、可信展示字段 |
| `CampusVerification` | 新增 | SSO 验证来源、验证状态、验证时间、撤销时间；不保存密码 |
| `Listing` | 第一阶段继续使用 `MarketItem` 表 | 标题、分类、成色、品牌型号、购入/使用时间、缺陷、配件、验货、交易地点/时间、可见联系方式、有效期 |
| `WantedPost` | 新增独立表 | 预算区间、期望成色、需求描述、校区、有效期、状态 |
| `TradeIntent` | 扩展 `MarketOffer` 语义 | 买方意向、报价、问题、建议时间、双方确认状态 |
| `TradeReservation` / `TradeRecord` | 从 `MarketOrder` 渐进迁移 | 只保存预约与成交事实，不保存商品收款/退款/结算状态 |
| `TradeReview` | 复用 `MarketReview` | 仅成交双方互评，保留申诉入口 |
| `ForumPost` / `ForumComment` | 复用 `Topic` / `Reply` | 板块收敛；增加通用内容关联 |
| `ContentLink` | 新增 | 连接广场帖子与商品、求购、学习资源、服务、活动 |
| `LearningResource` | 复用资料档案/版本/文件 | 原创声明、免费状态、许可、审核、版本、下载量；移除购买门槛 |
| `ResourceLink` | 复用 `ServiceCard` 或新增轻量表 | 官方入口、办事指南、地图/电话、可用状态 |
| `ServiceProvider` / `ServiceListing` | 新增 | 服务者认证、服务内容、价格说明、可用时间、评价、举报 |
| `PromotionOrder` | 新增并与学生交易完全隔离 | 仅平台增值曝光费，独立支付配置、回调和账务 |
| `AnalyticsEvent` | 新增 | 浏览、收藏、意向、发布、完成等最小化事件，不记录敏感明文 |
| `AdminActionLog` | 新增 | 管理员、动作、目标、理由、前后状态、时间、请求标识 |

### 4.3 目标状态机

实体商品：

`草稿 → 待审核 → 在售 → 洽谈中 → 已预约 → 已成交`

允许从在售/洽谈进入 `已下架 / 已过期 / 违规删除`；预约超时或取消后可按规则回到在售，并记录取消或爽约原因。不存在“待付款、已支付、退款中、已结算、待提现”。

求购：

`草稿 → 待审核 → 求购中 → 已收到报价 → 已匹配 → 已完成`

允许进入 `已取消 / 已过期 / 违规删除`。卖方通过结构化响应提交商品、报价、图片、成色、说明与可交易时间。

## 5. 当前权限系统

| 身份 | 当前能力 | 问题与调整 |
| --- | --- | --- |
| 游客 | 浏览公开论坛、市场、公告、服务等 | 可保留，但必须统一公开用户字段与联系方式脱敏 |
| 普通登录用户 | 发帖、回复、私信等 | 论坛目前不强制校内 SSO；目标需明确哪些互动必须校内认证 |

| `mod` | 论坛和市场部分管理能力 | 粒度过粗，可能接触数字交付或交易后台字段 |
| `admin` | 全站管理、配置、同步、支付与存储 | 权限过宽，缺敏感操作二次确认与操作日志 |

## 6. 当前商城交易流程

### 6.1 已有流程

卖家发布商品时会创建 `MarketItem`，上传图片，并自动关联一条论坛 Topic；买家可收藏、发起议价、私信。报价被接受后会生成 `MarketOrder`，实体商品进入保留状态，然后要求买家在 15 分钟内通过易支付完成付款。之后存在发货、完成、退款、争议、结算和卖家提现流程。

`listingType = wanted` 虽能表示求购，但仍共用商品表和商品详情；卖方响应主要靠私信，没有独立求购状态、结构化报价和匹配记录。

### 6.2 可保留能力

- 商品发布、编辑、图片、分类、收藏、浏览统计。
- 校内认证门槛。
- 会话与消息、站内通知。
- 议价记录可改造成 `TradeIntent`。
- 商品与论坛帖的关联思路。
- 成交后评价、举报、后台审核。

### 6.3 必须重构能力

- 删除实体商品“平台支付”主流程，改为预约和线下当面交易提示。
- 不再生成商品收款、退款、结算、提现任务。
- 求购从 `MarketItem.listingType` 拆为独立 `WantedPost`。
- 补齐品牌型号、使用时长、瑕疵、配件、验货、地点、时间、有效期和联系方式可见性。
- 商品与求购都需补齐审核、过期、违规下架状态。
- 详情页增加校内认证标识、安全提示、状态化分享文案、二维码/海报。

### 6.4 搜索与分享

当前全站搜索只真正覆盖论坛 Topic 和 `ServiceCard`，课程返回空数组，市场不是独立搜索域。更严重的是，搜索路由没有挂载统一的可选认证中间件，却自行读取 Bearer Token；当前 Web 使用 Cookie 会话，因此登录用户也可能被当作游客，导致论坛/市场结果缺失。

论坛已有分享链接和 PNG 分享卡，市场详情主要只有复制链接，缺商品状态、校区、价格、认证说明、二维码和交易安全提示。论坛分享组件与服务端卡片渲染可抽象复用。

## 7. 当前论坛结构

数据库目前有 12 个可见社区板块，分为 3 个分区，每区 4 个；另有隐藏市场板块和只读校园墙。当前帖子、回复均为空，说明收敛板块的迁移成本较低。测试代码还把“正好 12 个板块”当作固定规则，改造时必须同步测试。

建议目标只保留四个广场类别：

1. 求助与问答
2. 交易咨询与估价
3. 评价与避坑
4. 校园生活

原 Board 数据先映射并隐藏，不物理删除。`Topic`、`Reply`、点赞、匿名发布、图片/视频、AI 审核、举报与版主能力继续复用。需要新增通用 `ContentLink`，让广场内容可以关联商品、求购、学习资源、校园服务与活动，避免继续创建特殊板块。

## 8. 当前校园资源结构

当前校园资源包括：

- `/services` 服务导航、动态 eHall 应用和站内工具。
- `/academic` 基于 eBridge 的课表、成绩、考试等教务信息。
- 200 条已同步校园公告。
- 反馈、问卷、成绩核对、文件收集、PDF 工具。
- 后台可配置服务卡、工具权限、公告同步与站点功能。

数据库 `ServiceCard` 当前为 0，说明页面主要依赖动态/代码配置；历史 seed 中仍有其他学校和旧域名数据，不能用于西浦生产环境。`ACAD_PORTAL` 还会被重写到失效 `/jwxt`。

目标信息架构中，校园资源不再是主导航一级入口：

- 首页保留紧凑的常用资源区和官方公告区。
- “我的”中聚合已使用工具、收藏资源、文件任务和消息。
- `/services` 可保留为兼容入口并重命名“校园资源”，但从主导航降级。
- 学习资源成为独立免费内容中心，不与付费市场混放。

## 9. 支付相关代码位置与边界

当前支付分成两套：

1. `server/src/routes/payments.ts`、`EpayConfig`、`SponsorOrder`、`SponsorPaymentLog`：赞助墙/平台自营费用。
2. 市场路由、`MarketPaymentLog`、`MarketRefund`、`MarketSettlement`、`MarketPayoutProfile`、卖家中心：学生商品款、退款、结算和提现。

执行边界：

- **学生实体/二手商品：禁止平台代收、退款、结算、担保、提现和佣金。**
- **学习资料：改为免费原创内容，不再购买、不抽佣。**
- **平台自营：未来允许为置顶、推广位等增值服务收平台费用，但必须使用独立 `PromotionOrder` 和独立文案/账务，不能复用学生商品订单。**
- 现有支付表和日志先冻结、只读、保留，以免丢失历史证据；确认无历史交易且完成备份后，再决定归档。

当前数据库中没有市场订单和支付日志，易支付未启用，因此现在是切换边界的低成本窗口。

## 12. 安全与隐私风险

### P0：进入功能改造前处理

| 风险 | 证据与影响 | 处理建议 |
| --- | --- | --- |
| 市场公开接口暴露 `username` | 市场公开 seller 序列化直接包含用户名；SSO 场景下可能等同学号/校内账号 | 所有公开用户对象统一走脱敏 builder，非本人/授权管理员不得返回 username |
| “记住密码”并非安全存储 | Web 将学校账号密码放入 localStorage；加密密钥也在 localStorage，XSS 可同时读取 | 删除学校密码持久化，只记用户名；优先使用浏览器/系统凭证管理器 |
| 数据库迁移不可复现 | 63 个迁移目录只登记 2 个，且早期混有 SQLite 风格 SQL；直接 deploy 风险高 | 备份数据库，生成 PostgreSQL baseline，标记已应用状态，再建立可回滚的新迁移 |
| 产品仍允许学生商品平台收款 | 与“不碰学生商品款”边界冲突，带来支付、退款、结算和合规风险 | 关闭实体/求购支付入口、回调与佣金，先改成预约状态机 |
| 搜索认证失效 | 搜索只识别 Bearer Token，不识别现有 Cookie 会话 | 挂载统一 `authOptional`，补 Cookie 登录集成测试 |

### P1：首轮发布前处理

| 风险 | 处理建议 |
| --- | --- |
| `/schedule`、`/jwxt` 和桌面端旧认证接口为死链 | 提供兼容重定向或移除入口；更新原生壳与服务卡 |
| `ScheduleWidgetToken.jwxtToken` 可持久化学校令牌 | 路由当前未挂载且无数据；保持禁用，重构为短期不可逆凭证后才能恢复 |
| 公告同步配置持久化加密学校会话 | 增加明确 TTL、吊销、轮换、最后使用人和审计记录 |
| 支付与 QQ Bot 日志保存 `rawPayload` | 做字段白名单、密钥/账号脱敏、保留期限和清理任务 |
| `mod` / `admin` 权限过粗 | 引入权限点，限制数字交付、支付配置和敏感会话信息 |
| CORS 使用默认宽松配置 | 显式允许可信 Origin、方法、请求头和凭证组合 |
| 页面隐私承诺与能力不一致 | 登录页称只做身份验证，但 `/academic` 可读取教务数据；按功能做单独授权说明 |
| 原生 WebView 桥权限较大 | Android/Harmony 允许混合内容、文件/第三方 Cookie并暴露原生桥；限制 HTTPS 主域、可信 frame、下载来源和方法参数 |

### P2：治理增强

- 新增 `AdminActionLog`，覆盖审核、下架、封禁、配置、同步会话与支付配置操作。
- 新增数据保留策略、账号注销/导出流程、举报处置 SLA。
- 建立联系方式分级可见、图片 EXIF 清理、敏感文本与二维码检测。
- seed 脚本当前会清空业务数据并创建默认弱密码账号，应强制只在明确开发环境运行。
- 公告同步、微墙、QQ Bot、文件存储、学术数据应分别建立最小权限和密钥轮换手册。

现有安全基础中值得保留的部分：HttpOnly 不透明会话 Cookie、SameSite、CSRF 校验、加密的短期上游会话、上传大小/类型限制、AI 审核和举报机制。当前测试对 Cookie/CSRF 主流程已有覆盖。

2. 支持商品置顶、求购加急、首页推荐、商户主页和专题推广，并明确标注“推广/置顶/合作商户”。
3. 平台推广使用独立 PromotionOrder，只记录平台自营费用，初期支持订单记录和人工确认，不让自动支付阻塞上线。
4. 新增 AnalyticsEvent，覆盖曝光、详情、收藏、意向、预约、完成、分享和推广点击等运营漏斗。
5. 所有价格、分类、规则进入后台或配置，不写死在业务代码中。
6. 更新 PWA、Android、Flutter、HarmonyOS 入口和安全配置。

验收：服务与推广账务、学生交易数据完全隔离；推广内容有清晰标识；价格可配置；多端入口一致；数据可支持成交率、分享率和推广转化分析。

## F. 风险与回滚原则

- 不删除现有 MarketPayment / Refund / Settlement / LearningMaterialAccess 数据；先禁写、后归档。
- 所有旧路由先提供重定向或兼容响应，观察访问日志后再移除。
- 数据库每一阶段只做可回滚的小迁移；先备份、演练、再部署。
- MarketItem 等高关联表暂不物理改名，避免 ORM、API、测试和后台同时大面积断裂。
- 功能使用 feature flag 灰度：新首页、新交易状态机、新广场可分别回退。
- 原生壳与 Web 路由同时发布，避免新版页面与旧壳导航互相产生 404。
- 旧测试中固化的“12 板块、付费资料、易支付订单”应改成新产品规则，不能把旧测试通过当作新需求正确。

## G. 测试与验收清单

- 权限：游客、普通登录、校内认证、审核员、管理员各自可见字段和操作。
- 隐私：公开 API 不含学号/登录名、上游 Token、密码、支付/QQ 原始敏感字段。
- 状态机：商品、求购、意向、预约、完成、取消、过期、违规的合法/非法迁移。
- 支付边界：学生商品和学习资料无法发起支付；仅平台推广可创建 PromotionOrder。
- 兼容：旧商品、论坛帖子、学习资料、服务和个人页 URL 可跳转。
- 搜索：Cookie 登录下覆盖商品、求购、广场、学习资源、服务。
- 分享：状态、价格/预算、校区、安全提示、二维码正确，隐藏联系方式。
- 数据库：空库可完整部署，现有库可增量升级并回滚。
- 多端：Web、PWA、Android、Flutter、HarmonyOS 五栏和深链一致。
- 视觉：Logo、品牌紫、图标、暗色模式、卡片语言保持一致；重点检查 360px、768px、桌面宽度。

## 阶段 0 最终判断

当前最适合的路线是：**保留现有主技术栈和多数底层模块，先完成阶段 0.5 的安全与支付边界封口，然后再做首页/导航和交易状态机。**

当前数据库没有市场交易数据，论坛也没有用户帖子，是完成定位切换的较好窗口。只要先建立可靠迁移基线、停止学生商品支付和付费资料、修复隐私泄露与认证死链，后续可以按模块渐进上线，无需停站式重写。
